Codex 是怎么干活的：组件、调度、代价

发表于 2026-09-30 分类于 Tech 本文字数： 4k 阅读时长 ≈ 4 分钟

1. 从一次测试说起

你让 Codex 跑一次测试。界面在等你，本地有个进程在干活：它读你的代码，决定跑哪条命令，中间可能停下来问你一句，把输出带回来，改几个文件，再跑一遍。

这篇讲的是这个进程内部怎么组织：活怎么排队，命令怎么被拦住，状态存在哪，每个设计付了什么代价。

2. 它长什么样

按”这块负责什么”来分，比按代码目录分好记。

这块负责什么内容源码位置
跟客户端说话定义消息格式，收事项、发事件；外面再包一层 JSON-RPC，给编辑器插件、终端、远程连接用codex-rs/protocol、codex-rs/app-server*
管一轮对话的状态轮次、步骤、输入排队、上下文上限、从日志重建core/src/session/
记住谁在跑什么当前活跃轮次、正在跑的任务、任务类型、本轮用了多少 tokencore/src/state/
区分四种任务对话、压缩、审查、shell 命令；由触发点决定走哪个core/src/tasks/
管工具调用工具登记、分发、三道判断、并行执行core/src/tools/

这些块摆在一起是这样：

图 1 · 引擎里的分工

客户端只负责显示和传话，剩下的事都在引擎里。引擎内部大致是”接口 → 会话 → 调度 → 工具”这样一层层往下。沙箱、日志、扩展点这几样不归某一层，每一层都要用。

3. 一条命令走完的路径

先说消息怎么进来。客户端不直接调用引擎里的函数，而是把要做的事放进一个队列，引擎把发生了什么放进另一个队列。源码里这两个队列叫 SQ 和 EQ。

这一步看着多余。同一个进程里直接调函数不是更快？快是快，代价是客户端必须和引擎用同一种语言、同一个版本、跑在同一台机器上。改成队列之后，终端、编辑器插件、远程连接、第三方产品都能接进来，代价是每改一次消息格式，都得想清楚老客户端怎么办。

消息进来之后先排队。引擎把输入放进输入队列，开一个回合。回合里再分步骤：一次模型请求，加上它触发的工具调用。输入队列是独立的一块，所以它跑着的时候你还能插一句话，不用等它结束。

接着事情会被归到四类任务里：正常对话、压缩上下文、代码审查、你自己敲的命令。这里没有”挑一个”的动作，谁来触发是确定的——普通消息就是对话，上下文接近上限就是压缩，跑审查就是审查，你直接敲的命令就是命令任务。引擎只需要记下当前是哪一类，用来记账、决定怎么中断、发什么事件。

命令真正开跑之前，还有三道判断，下一节单独说。

跑完的结果会变成一条记录，通过事件队列推回客户端。中断留了 100 毫秒的宽限，并在历史里记一笔，保证日志事后还看得懂。

4. 命令开跑前的三道判断

要执行 pnpm test，有三件事得先定下来。

第一件，要不要停下来问你。命令在允许列表里就直接跑；不在，就问你，并且可以顺手记成规则，下次同类命令不再问。

第二件，放进哪个范围跑。只读、可写当前工作区、还是完全放开。默认是可写工作区，网络默认关闭。

第三件，被拦下来怎么办。如果沙箱因为断网把命令拒了，它带着这个原因再来问你一次；你同意后按更宽的范围重试，而且不会把同一个问题再问一遍——上次的决定被记住了。

这三件事都是算出来的，不是谁在现场拍板。输入就这些：命令本身、配置里的允许列表、当前的沙箱范围、你上一次的回答。

关键在于，这三步在源码里集中在一个地方（tools/orchestrator.rs），所有工具都走这条路。如果让每个工具自己判断，会出现几个具体毛病：同一条命令从不同工具发起时问法不一样；你刚点过同意，换个工具又问一遍；报错话术各写各的，排查时要翻十几个地方。

5. 输出为什么要截掉一半

长命令的输出不会原样全存。实现是一个对半分的缓冲：一半留给开头，一半留给结尾，中间丢掉，并在丢掉的位置写一行”这里省略了多少字节”。

理由很实在。开头有命令回显和第一处报错，结尾有最终结论，中间通常是又长又重复的日志。上下文是有名额的，一次 npm install 的日志能顶掉好几轮对话。

代价也直接：万一关键信息落在中间，就真丢了，只能靠那行提示知道该重跑一次。

6. 上下文是从会话日志里长出来的

上下文不是内存里那份随时被改的东西，而是从会话日志推出来的。恢复上次的会话、回滚几轮、压缩之后接着跑、审查历史改动，靠的都是这一条。

上限也不是感觉，是几个具体数字：这个模型能装多少、这一轮用了多少、哪些内容必须保留。

压缩同样是一个可以被调度、被中断、被记账的任务，不是偷偷发生的动作。它和上一节那三道判断是同一个思路：把藏在里面的行为变成能看见的对象。

7. 代价

前面每节只说了做法，这里说说代价。

用两个队列通信，换来了可替换，代价是兼容。直接调函数最简单也最快，但客户端就得和引擎同进程、同语言、同版本。改成队列以后，多端都能接进来，代价是每次改消息格式都要想清楚老客户端怎么办。这笔账只在”客户端会很多”的前提下划算；如果只是自己用的一个终端界面，队列就是多余的一层。

把三道判断集中在一处，换来了一致，代价是风险集中。不集中会出现前面说的那些毛病：问法不一样、重复询问、话术各写各的。集中之后它们一次性消失，但那一处代码成了所有工具调用的必经之路，改它就是在动全局，所以它必须简单、必须能测。

其余几个选择的代价，列在这里。

  • 所有命令走同一个执行通道：策略只有一份，但进程状态、输入确认、输出截断都得自己实现。
  • 输出掐头去尾：上下文不被长输出冲垮，代价是关键信息可能落在中段。
  • 压缩做成正经任务：能看见、能中断、能记账，代价是多一次模型调用、多一处状态。
  • 沙箱枚举加规则两套配置：默认开箱即用，代价是两套不能混用，配置面变重。
  • 子 agent 隔离上下文：主线不被日志淹没，代价是用量成倍。
  • 钩子只开固定几个事件：简单、稳定、可测，代价是覆盖不到的事件挂不上。

8. 可以借用的做法

四条。

越过你的判断只写一遍。要不要问人、放什么权限、失败怎么重试，集中到一条路径上。散着写，最后一定会出现同一件事三种问法。

所有命令走同一个通道。这样才能谈一致的行为和可观测。每个工具自己起进程，出事的时候你得先花半天找是哪个工具干的。

上下文从日志来，不从内存来。内存里那份状态只活在进程里，日志才撑得起恢复、回滚、审查。

上限写成数字。”尽量精简”没法检查，”最多占上下文 2%”可以。

代价是工程量。这四条不做，项目照样能跑，区别在出问题的时候你有没有地方查。
